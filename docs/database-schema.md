# Minimal database schema

This is a proposed logical SQLite schema, not an applied migration. IDs are application-generated UUID text; timestamps are UTC ISO 8601 text. JSON columns are validated with Zod before persistence. Enable `PRAGMA foreign_keys = ON` on every connection; SQLite foreign key enforcement is connection-specific ([SQLite documentation](https://www.sqlite.org/foreignkeys.html)).

| Table | Columns and constraints |
| --- | --- |
| `sources` | `id` PK; `requested_url`, `final_url`, `title`, `content_text`, `content_sha256`, `extractor_version`, `fetched_at` NOT NULL. Immutable once accepted. |
| `passages` | `id` PK; `source_id` FK sources; `ordinal`, `start_offset`, `end_offset`, `text` NOT NULL; UNIQUE(source_id, ordinal). Offsets are Unicode code-point offsets in normalized content, start inclusive/end exclusive. |
| `sessions` | `id` PK; `source_id` FK sources UNIQUE; `status` CHECK (`source_ready`, `exploring`, `practising`); `budget_usd_micros` nonnegative; `created_at`, `updated_at`. Sessions remain available for future reviews rather than ending after one assessment. |
| `concepts` | `id` PK; `session_id` FK sessions; `name`, `explanation`, `prerequisites_json`, `passage_ids_json` NOT NULL. |
| `messages` | `id` PK; `session_id` FK sessions; `ordinal`, `role` CHECK (`user`, `assistant`); `content`, `claims_json`, `created_at`; UNIQUE(session_id, ordinal). Claim records distinguish article evidence, illustration, and supplementary/unverified knowledge. Only validated tutor responses are accepted. |
| `attempts` | `id` PK; `concept_id` FK concepts; nullable `parent_attempt_id` FK attempts; `ordinal` positive; `kind` CHECK (`baseline`, `probe`, `changed_example`, `review`, `writing`); `audience`; `status` CHECK (`draft`, `submitted`, `evaluated`); frozen `prompt`, `criteria_json`, `passage_ids_json`; `input_mode` CHECK (`typed`, `spoken`); `draft_text`; nullable `initial_transcript`, immutable `submitted_text`, `submitted_at`, `confidence_report_json`; `created_at`, `updated_at`; UNIQUE(concept_id, ordinal). No audio or fixed question count. |
| `assistance_events` | `id` PK; `attempt_id` FK attempts; `kind` (hint, correction, prior-answer reveal, or other help); `content`, `created_at`; nullable `message_id` FK messages. Record help before and during the attempt so evidence is not falsely labelled unaided. |
| `evaluations` | `id` PK; `attempt_id` FK attempts; `revision` positive; nullable `supersedes_id` FK evaluations; `result_json`, `evaluator_version`, `created_at`; UNIQUE(attempt_id, revision). Immutable criterion judgments, separate reasoning/clarity feedback, evidence, gaps/actions, and uncertainty; no aggregate score. |
| `feedback_challenges` | `id` PK; `evaluation_id` FK evaluations; `clarification`, `status` CHECK (`pending`, `resolved`, `uncertain`); nullable `resolution_evaluation_id` FK evaluations; `created_at`. Preserve the disputed judgment and clarification; new substantive reasoning belongs to a new attempt. |
| `review_plans` | `concept_id` PK/FK concepts; `revision` positive; `due_at` UTC timestamp; `time_zone`, `rule_version`; `basis_attempt_id` FK attempts; `learner_override` CHECK 0/1; `email_enabled` CHECK 0/1; `updated_at`. One current plan per concept, including overdue plans. |
| `reminders` | `id` PK; nullable `concept_id` FK concepts ON DELETE SET NULL; `plan_revision`; `request_key` UNIQUE; `scheduled_for`; `provider`; nullable `provider_message_id`; `desired_state` CHECK (`scheduled`, `cancelled`); `status` CHECK (`pending`, `scheduled`, `cancelled`, `finished`, `failed`, `unknown`); nullable `error_code`; `created_at`, `updated_at`. Minimal external reconciliation record may outlive deleted learning data. |
| `email_calls` | `id` PK; `reminder_id` FK reminders; `kind` CHECK (`schedule`, `cancel`, `reconcile`); `request_key` UNIQUE; `status` CHECK (`pending`, `succeeded`, `failed`, `unknown`); nullable `provider_request_id`, `estimated_cost_usd_micros`, `error_code`; `usage_basis` CHECK (`reported`, `estimated`, `unknown`); `pricing_json`, `created_at`; nullable `completed_at`. No learning content. |
| `ai_operations` | `id` PK; `session_id` FK sessions; nullable `attempt_id` FK attempts; `idempotency_key` UNIQUE; `task` CHECK (`concepts`, `tutor`, `prompt`, `evaluate`, `reconsider`, `transcribe`); `status` CHECK (`pending`, `succeeded`, `failed`, `interrupted`); `input_hash`, `prompt_version`, `schema_version`, `created_at`; nullable `completed_at`, `error_code`. Transcription metadata must not retain audio. |
| `ai_calls` | `id` PK; `operation_id` FK ai_operations; `attempt` positive integer; `provider`, `model`, `pricing_json`, `reserved_usd_micros`, `status`, `started_at`; nullable `provider_request_id`, `input_tokens`, `output_tokens`, `audio_duration_ms`, `estimated_cost_usd_micros`, `finished_at`, `error_code`; `usage_basis` CHECK (`reported`, `estimated`, `unknown`); UNIQUE(operation_id, attempt). Cost arithmetic uses integer micro-USD, rounded upward. |

Use NOT NULL for required fields described above, CHECK constraints for nonnegative usage/costs and ordered offsets, and indexes on child foreign keys. `ai_calls.status` uses `pending`, `succeeded`, `failed`, or `unknown`. `pricing_json` freezes currency, per-token rates, pricing date, and any supported cached-token rates. Transcription pricing snapshots also freeze supported duration rates and rounding; token fields may be null. Avoid provider features with unsupported billing units. Store email request attempts, provider request IDs, usage/cost basis, and failures in a separate `email_calls` ledger linked to reminders, with its own cost limit. An accepted schedule is not proof of delivery. Recipient address and delivery preferences are single-learner server-side settings, not a user-account model; never return credentials to the browser.

Relations: source → passages and one session; session → concepts/messages/AI operations; concept → repeatable attempts and one review plan; attempt → assistance/evaluation revisions; evaluation → challenges; reminder → external email attempts. Child FKs use ON DELETE CASCADE unless noted. No user table is required for one local learner.

JSON keeps criteria and feedback small. Transactions must enforce membership: cited passages belong to the session's source; attempt parents and review basis belong to the same concept; evaluation/challenge revision links belong to the same attempt; assistance messages belong to the same session. The database cannot enforce JSON references as foreign keys. Normalize these relations if integrity/reporting needs grow. Enforce acyclic revision links, one current evaluation per attempt, and only one deliberate active reminder per concept across plan revisions using transactions and appropriate partial unique indexes. Unknown remote state requires reconciliation, not blind replacement.

Transitions and atomicity:

- Failed fetching/extraction creates no accepted source. Accepted source, passages, and session are written together.
- Valid concept generation advances `source_ready → exploring`; creating the first frozen attempt advances the session to `practising`. Concepts without attempts remain unassessed.
- Save draft text and corrected transcripts across reload. Freeze prompt and criteria when creating the attempt, before display. Confirm one nonblank response before `draft → submitted`, then freeze the submitted response. Do not expose expected reasoning before submission.
- A validated evaluation revision advances `submitted → evaluated`. Failed evaluation leaves the submitted attempt intact. Duplicate submission/evaluation requests do not create duplicate deliberate calls or revisions.
- A challenge appends clarification and optionally a linked evaluation revision. Preserve the original judgment; unresolved disputes remain uncertain. Reconsideration is distinct from a retry or a new learning attempt.
- Changed-example, review, and writing practice create new attempts. Prior-answer reveal or tutor help creates assistance events; an immediate retry after correction is never silently labelled independent.
- Commit accepted feedback and the review-plan change atomically. Reminder dispatch occurs after commit, outside the transaction. A scheduling failure cannot roll back learning results or erase a due date. Store a stable reminder request key before dispatch and reconcile interrupted/unknown outcomes on app restart/open or explicit retry.
- Changing a plan marks the old remote reminder for cancellation; reconcile before replacement. Keep failed/unknown cancellation visible. After its scheduled time/reconciliation, mark a reminder finished when it is no longer active; this does not prove delivery. Missed reviews remain due without generating repeated messages.
- Session deletion blocks active learning/transcription calls, marks remote reminders for cancellation, and deletes learning records transactionally. Preserve minimal reminder/email-call metadata needed for reconciliation without answers, feedback, or article text; purge it after resolution. Remote delivery can race with deletion, so do not claim unsent messages were cancelled until confirmed.
- Record every external attempt, including failures. Persist operation completion and accepted learning results in one transaction. Use a partial unique index for one pending AI operation per session and transactional session/day reservations. A repair call belongs to the original operation; a user retry has a new operation/key with explicit lineage.

No dashboard or permanent mastery table: derive dated evidence from attempts, current evaluation revisions, assistance, and review plans. Optional confidence reports are learner self-reports, not evaluator judgments. Exact scheduling intervals and provider-specific reminder reconciliation remain proposed implementation details.
